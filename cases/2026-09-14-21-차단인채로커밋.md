패턴 이름: **차단인채로커밋**
날짜: 2026-09-14 (2회, 같은 날)
근거: instructions-log.md 지시 #78(1회차 `bfd4766`) · 지시 #88(2회차 `5a567ca`)

## 상황
절차 30 은 **커밋 전에** `python checks/run.py` 를 돌리라고 한다.
나는 두 번 다 `checks/run.py && git commit` 을 **한 명령줄에 이어 붙여** 돌렸다.
검사 결과가 화면에 찍히는 시점에는 이미 커밋이 끝나 있다.

## 결과
- **1회차** `bfd4766` — 새 제안서에 예측·반증 절이 없어 `c4` 가 **차단 1**. 다음 커밋에서 고쳤다.
- **2회차** `5a567ca` — `zoneDPS` 를 고치면서 `ZOMBIE_DPS_RATIO` 를 없앴는데 `c16`·`c13`·`gen_balance_csv` 가 그 이름을 계속 찾아 **차단 1**(c16). 다음 커밋에서 고쳤다.

둘 다 "다음 커밋에서 고쳤다" 지만, **저장소 이력에 차단 상태인 커밋이 남는다.**
그 커밋을 집어 되돌리면 깨진 상태가 살아난다.

## 판단 — 처음 쓴 원인이 틀렸다. 실행으로 확인했다

처음엔 "`checks/run.py` 가 차단인데도 종료 코드 0 을 낸다" 고 적었다. **틀렸다.**
그 스크립트는 `return 1 if blocking else 0` 으로 제대로 1 을 낸다. 확인:

```
python -c "import sys; sys.exit(1)"            → 종료 1
python -c "import sys; sys.exit(1)" | tail -2  → 종료 0   ← 이것이다
```

**진짜 원인**: 내가 출력을 줄이려고 `python checks/run.py 2>&1 | tail -2 && git commit` 으로 썼다.
**파이프라인의 종료 코드는 마지막 명령(`tail`)의 것**이라 앞의 1 이 삼켜진다. `&&` 가 못 막는다.
두 번 다 같은 한 줄을 썼다. **글로 적힌 절차를 명령줄 습관이 이겼다.**

## 교훈
1. **사람 손(내 손)이 지켜야 하는 절차는 두 번 이상 어긴다.** 기계로 내려야 한다.
2. 막는 자리는 커밋 **직전**이어야 한다 — 보고가 아니라 **거부**여야 한다.

## 고친 것
- `rules/R007-차단이면커밋안한다.md` 승격 (같은 패턴 2회, 절차 40).
- `tools/install_hooks.py` + `.githooks/pre-commit` — **git 이 커밋을 거부한다.** `checks/run.py` 를 돌려 차단이 하나라도 있으면 종료 코드 1.
  `git config core.hooksPath .githooks` 로 켠다. 저장소에 따라 들어가므로 새로 받은 사람도 같은 보호를 받는다.
- `checks/run.py` 는 **이미** 차단이면 1 을 낸다. 고칠 게 없었다 — 고칠 것은 **내 명령줄**이었다.
  훅은 파이프 없이 `python checks/run.py` 를 그대로 돌리므로 종료 코드가 안 삼켜진다.
