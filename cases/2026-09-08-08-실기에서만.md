# 사례 — 실기 폰에서만 한글이 깨졌다

패턴 이름: **실기에서만**
날짜: 2026-09-08
근거: instructions-log.md 지시 #15 · 사람이 LG V30에서 직접 확인

## 상황
WBS 1.2~9.2 를 자동으로 진행하며 브라우저에서 여러 번 확인했다.
세로 375×812 에뮬레이션, 가로 1000×520, 좌표 변환, 백버퍼 정합, 밸런스 시뮬레이션 — 전부 통과.
검사 10개도 전부 통과. 자가진단 10/10.

## 판단
브라우저 확인과 검사가 다 통과했으니 화면 쪽은 문제가 없다고 봤다.

## 결과
사람이 LG V30에서 `content://media/...` 로 파일을 열자 **한글이 전부 깨졌다.**
원인은 단순했다 — **문서에 `<meta charset="utf-8">` 선언이 없었다.**
데스크톱 브라우저는 로컬 파일을 UTF-8 로 짐작해 통과시켰고, 안드로이드는 레거시 인코딩으로 떨어뜨렸다.

같이 확인하다 **뷰포트 meta 도 없다**는 것을 발견했다. 이건 지적받지 않은 것이다.
- 모바일 브라우저가 가상 뷰포트 980px 를 쓴다 → 지시 #12에서 맞춘 백버퍼 정합이 다시 어긋난다
- `viewport-fit=cover` 가 없어 `env(safe-area-inset-*)` CSS 가 죽은 코드였다

## 교훈
1. **에뮬레이션은 문서 인코딩과 뷰포트 협상을 재현하지 못한다.** 이 둘은 실기에서만 드러난다.
2. WBS 10.1(폰 실기 확인)을 "기계가 못 하는 일"로 분류하고 자동 진행의 정지 조건으로 못 박아 둔 판단이 맞았다.
   그 정지 조건이 없었다면 깨진 채로 "완료" 보고했을 것이다.
3. 선언이 없으면 기기에 따라 **반드시** 깨진다. 판단이 갈리는 문제가 아니라 결정적인 문제다
   → 1회 관측이지만 바로 검사로 내렸다 (`checks/c10_html_meta.py`, 1순위)

## 남는 한계
이 사례는 **사람이 실기에서 열어봤기 때문에** 잡혔다.
기계가 대신할 수 없는 확인이 여전히 존재한다는 증거다. 10.1 을 자동화 목록에 넣지 않는다.
